Updating the kit

An update is a newer copy of the kit. Your version is in kit/VERSION, and kit/CHANGELOG.md says what each one changes for a running site: read it before updating. Most of it takes effect the next time the site starts: the stacks, Traefik's routes, the bridge, and the dashboards and alerts (made again for your site at every start). Two things you upload yourself: the theme and the short links. Your site.env, secrets/ and data/ are never touched.

Before you update

  • Take a backup. Ghost moves its database forward when a newer Ghost starts, and an older Ghost can't read it afterwards. The backup is the only way back.
  • Note where you are, so you can see what changed and come back to it: 
    git rev-parse --short HEAD          # write this down
  • Pick a quiet moment: no live show, nothing scheduled to publish in the next few minutes.
From a ZIP

No git? Download the new ZIP, unzip it beside the old copy, and move your site's folder (kit/sites/mysite) into the new one; then run the commands below from the new copy, without git pull. Keep the old copy until the site runs well: it's your way back (going back is the same move the other way, with the backup). Where the steps below use git diff, compare the two copies instead: diff -rq old/kit/theme new/kit/theme and diff old/kit/redirects.yaml new/kit/redirects.yaml for the theme and short links, diff of their instances/example.env and stacks/*/.env.example for the settings.

On Docker Compose

git pull
kit/kit.sh kit/sites/mysite pull --ignore-buildable   # the images this version names (the changelog says which changed)
kit/kit.sh kit/sites/mysite up -d                     # recreates what changed

Ghost may take a minute or two to start the first time after a new version, while it updates its database. Don't stop it meanwhile: a Ghost stopped in the middle of that leaves its database locked (the fix).

On Kubernetes

git pull
k8s/up.sh kit/sites/mysite <overlay> --render            # look first, if you like
k8s/up.sh kit/sites/mysite <overlay>

The kit's own three images are this version's published ones, so the cluster picks up the new ones by themselves (if you build them yourself instead, run k8s/build-images.sh again first: the Setup guide). up.sh waits until every part is ready again and stops with the reason if one isn't.

The theme and the short links

See whether the update changed them:

git diff --stat <the version you noted> HEAD -- kit/theme kit/redirects.yaml
  • The theme changed: download puppi3-creator-kit-theme.zip from the new version's release and upload it in Ghost (Settings, Design & branding, Customize, Change theme, Upload theme). Its settings, like the Live stream URL, stay as they were.
  • The short links changed: upload kit/redirects.yaml again (Settings, Labs (under Advanced: Open, Beta features), Redirects). If you've added your own lines to it, keep your copy and add the new lines to it.

New settings

A new setting starts with its default, so nothing needs adding for the site to keep working. To see what's new:

git diff <the version you noted> HEAD -- instances/example.env stacks/*/.env.example kit/examples k8s/examples

The Settings reference explains each one.

Going back

If the new version misbehaves: git checkout <the version you noted>, put the backup back (below), and start the site again. Putting back only the old code isn't enough once a newer Ghost has updated the database. Then come back to the newer version: git checkout main (or the branch you follow).

Backups

A site's folder holds nearly everything: site.env, secrets/ and data/ (Ghost's database and files, Postiz's databases and uploads, the bridge's history, the stream server's settings, Grafana's and Prometheus's data). The exception is the analytics: on Compose, Tinybird keeps its data in four Docker volumes named after the site's short name (ID_PREFIX): <short name>_tinybird_clickhouse, _tinybird_redis, _tinybird_files and _traffic_analytics_data. A backup that leaves them out loses the visitor numbers, nothing else.

Never down -v

kit/kit.sh <folder> down -v deletes those volumes, and with them every visitor count. Use stop or down without -v, unless you're removing the site for good.

A backup holds the site's passwords and keys (secrets/). Keep it somewhere private, and keep one copy away from the machine that runs the site.

Everything, with the site stopped

The whole site, as it is, in a few minutes of downtime. The safest kind: the databases are closed, so nothing is half-written. Set ID to the site's short name.

ID=mysite; B=~/backups/$ID-$(date +%F); mkdir -p "$B"
kit/kit.sh kit/sites/mysite stop
tar -czpf "$B/folder.tar.gz" -C kit/sites mysite
for v in $(docker volume ls -q --filter label=com.docker.compose.project=$ID); do
  docker run --rm -v $v:/v:ro -v "$B":/b busybox:1.37.0 tar -czf /b/$v.tgz -C /v .
done
kit/kit.sh kit/sites/mysite up -d

On Linux, run the tar line with sudo: each part of the site owns its own folders, and the backup has to read them and keep their owners.

The databases, while it runs

For a nightly copy with no downtime, dump the databases, which hold what changes most (posts, members, settings, the social queue), and copy Ghost's files:

B=~/backups/mysite-$(date +%F); mkdir -p "$B"
kit/kit.sh kit/sites/mysite exec -T db sh -c \
  'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --no-tablespaces ghost' | gzip > "$B/ghost.sql.gz"
kit/kit.sh kit/sites/mysite exec -T postiz-postgres pg_dump -U postiz postiz | gzip > "$B/postiz.sql.gz"   # with social
tar -czf "$B/ghost-content.tar.gz" -C kit/sites/mysite/data/ghost/ghost content
(cd kit/sites/mysite && tar -czf "$B/settings.tar.gz" site.env secrets data/ghost/ghost/config.production.json \
  $(ls data/ghost/tinybird/tokens.env 2>/dev/null))   # the settings, Ghost's mail login, the analytics' tokens

A site made before kit 1.2.0 keeps Ghost's files in data/puppi3/ instead of data/ghost/ (the kit uses whichever the site has): write puppi3 for ghost in those paths.

The warning about a password on the command line is MySQL's own, and harmless here: it's the container's own password, inside the container. Ghost's database is called ghost unless you changed database__connection__database. These copies don't include the analytics or the dashboards' history: take a stopped backup now and then for those.

Putting a backup back

On the same machine or a new one, with this repo at the same version as when the backup was made. The short name stays the same (it names the volumes):

ID=mysite; B=~/backups/mysite-2026-10-12
kit/kit.sh kit/sites/mysite down 2>/dev/null; rm -rf kit/sites/mysite     # only if an old copy is there
docker volume rm $(docker volume ls -q --filter label=com.docker.compose.project=$ID) 2>/dev/null
tar -xzpf "$B/folder.tar.gz" -C kit/sites                                    # sudo on Linux
kit/kit.sh kit/sites/mysite create                                           # makes the empty volumes
for f in "$B"/${ID}_*.tgz; do v=$(basename "$f" .tgz)
  docker run --rm -v $v:/v -v "$B":/b busybox:1.37.0 tar -xzf /b/$v.tgz -C /v
done
kit/kit.sh kit/sites/mysite up -d

From a nightly copy instead, put the database back into a running site:

gunzip -c "$B/ghost.sql.gz" | kit/kit.sh kit/sites/mysite exec -T db sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" ghost'
kit/kit.sh kit/sites/mysite restart ghost

On Kubernetes

  • Your own cluster (selfhosted): the databases run in the cluster. Dump them the same way through kubectl, and copy Ghost's files out of its pod: 
    NS=mysite
kubectl -n $NS exec mysql-0 -- sh -c 'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --no-tablespaces ghost' | gzip > ghost.sql.gz
kubectl -n $NS exec postiz-postgres-0 -- pg_dump -U postiz postiz | gzip > postiz.sql.gz
kubectl -n $NS exec deploy/ghost -c ghost -- tar -czf - -C /var/lib/ghost content > ghost-content.tar.gz
    Your cluster's own volume snapshots, if it has them, cover everything else.
  • EKS or GKE: switch on the cloud's automatic backups for both databases (RDS's backup retention, Cloud SQL's automated backups), and versioning on the bucket that holds Ghost's images and files. Keep the site's folder (site.env, secrets/, the cloud file) backed up yourself: the cloud doesn't have it.
  • Everything at once: moving the site to a Compose host with to-nas.sh (below) brings all of it, analytics and history included.

Moving a site

The same site can run on Docker Compose or Kubernetes, and move between them with its data: posts, members, pictures, the social queue and history, the analytics, the stream server's settings and the dashboards' history.

From → toHow
One Compose machine → anotherA stopped backup, put back on the new machine, then the DNS
Compose → Kubernetesk8s/migrate/to-cloud.sh (below)
Kubernetes → Composek8s/migrate/to-nas.sh (below)
One cluster → anotherThrough a Compose site: to-nas.sh into it, then to-cloud.sh into the other cluster
One copy at a time

Postiz, Temporal and the bridge must run in one place only. Two bridges would share every post twice, and two Postiz would publish queued posts twice. The migration scripts stop them on the side the site leaves, and they stay stopped. Don't start that side again with kit.sh up or up.sh while the site lives on the other.

What the migration scripts do

Both run on your own machine, with kubectl pointed at the cluster. They reach the Compose side's containers and data folder either on this machine or over ssh (with sudo there). Their messages call that side "the NAS".

  • They show what moves and what stops, and ask first. -n only checks both sides and prints the steps; -y doesn't ask.
  • They count every database and folder on both sides at the end, and stop with exit code 3 if any differ.
  • Ghost's database only goes to the same Ghost version or a newer one: they stop before copying if the other side's Ghost is older.
  • They never touch your DNS: you point the names at the new place yourself, once you've checked it.
  • Over ssh, they ask once for the password (ssh and sudo). On a Mac they look in your Keychain first, under <short name>-nas, account = your user there: security add-generic-password -s mysite-nas -a <user> -w saves it.

Compose → Kubernetes

  1. The cluster's folder. A second folder for the cluster, with the same site.env and the same secrets (the data that moves was made with them): 
    mkdir -p kit/sites/mysite-k8s/data/icecast/tinyice-data
cp -Rp kit/sites/mysite/site.env kit/sites/mysite/secrets kit/sites/mysite-k8s/
cp -p kit/sites/mysite/data/icecast/tinyice-data/config.json kit/sites/mysite-k8s/data/icecast/tinyice-data/
    Keep ID_PREFIX as it is: the scripts find the site by it on both sides. Add secrets/ghost-mail.env (Ghost's mail, from the mail part of data/ghost/ghost/config.production.json, one setting per line). For EKS or GKE, add the cloud's file and secrets as the setup guide says. Behind Cloudflare, use TLS_RESOLVER=cf: it gets certificates from anywhere.
  2. The empty site up, a day or so before: run k8s/up.sh kit/sites/mysite-k8s <overlay>. Check it through the cluster's own address (how) while the Compose site keeps serving.
  3. Freeze. From now until the DNS points at the cluster: no edits or new posts in Ghost Admin, nothing scheduled to publish, no live show. Anything written on the Compose side after the copy starts stays behind.
  4. Move. A dry run, then the real one. The data folder is the Compose site's data/, here or on another machine: 
    k8s/migrate/to-cloud.sh kit/sites/mysite-k8s <overlay> --from <user>@<host>:/path/to/mysite/data -n
k8s/migrate/to-cloud.sh kit/sites/mysite-k8s <overlay> --from <user>@<host>:/path/to/mysite/data
    It stops Postiz, Temporal and the bridge on the Compose side (for good), copies everything, and ends by starting the site in the cluster with up.sh.
  5. Check, still through the cluster's own address: the front page, a post with its pictures, signing in to Ghost Admin (a code arrives by mail), Postiz's channels, Grafana's history.
  6. Point the DNS at the cluster: the site's names at traefik's address, and a name that isn't proxied by Cloudflare at tinyice-source's, for your streaming software. If you put your own address in TRUSTED_EXTRA for the check, take it out and run up.sh again. Then end the freeze.

The Compose side keeps its copy, its social part stopped. Leave it so until you move back, or until you're sure, then kit/kit.sh kit/sites/mysite stop. Never up -d it while the site is in the cluster.

Kubernetes → Compose

The same freeze, the other way. The Compose site must be there, set up with the same site.env and secrets: the one the site left, or a new one made with kit/setup.sh and started once. Its databases must be running: if you stopped it, start only those, so the bridge stays off:

kit/kit.sh kit/sites/mysite start db postiz-postgres postiz-temporal-postgres prometheus   # the ones your modules have

Then:

k8s/migrate/to-nas.sh kit/sites/mysite-k8s <overlay> --to <user>@<host>:/path/to/mysite/data -n
k8s/migrate/to-nas.sh kit/sites/mysite-k8s <overlay> --to <user>@<host>:/path/to/mysite/data
  • It keeps what the Compose side had first, in data/.migrate-backups/<date>/, then replaces it and starts Ghost, the analytics, the stream server, Postiz and the bridge there. --no-start leaves them stopped.
  • If it says Tinybird's tokens differ, it has written the new ones: recreate the parts that read them, then start everything as usual (that also gives Grafana back its view of Postiz's tables): 
    kit/kit.sh kit/sites/mysite up -d --force-recreate ghost traffic-analytics postiz-ghost-bridge
kit/kit.sh kit/sites/mysite up -d
  • Point the DNS back, check the site, end the freeze. The cluster keeps its copy, its social part stopped, until k8s/up.sh kit/sites/mysite-k8s --down deletes it. In a cloud, delete what costs money too (the cluster, databases and bucket).

Troubleshooting

First look

On Compose, see which parts are running and read the logs of the one that isn't:

kit/kit.sh kit/sites/mysite ps                     # anything not "Up", or restarting
kit/kit.sh kit/sites/mysite logs --tail 100 ghost  # one part's last lines; -f to follow

On Kubernetes, the namespace is the short name:

kubectl -n mysite get pods
kubectl -n mysite describe pod <pod>         # its Events, at the bottom
kubectl -n mysite logs <pod> --previous      # why it stopped, if it restarted
PartCompose serviceWhat it is
Sitetraefik, ghost, dbThe router in front (https, Cloudflare-only), Ghost, its MySQL
analyticstinybird-local, tb-setup, tinybird-sync, traffic-analyticsWhere page views are kept, its one-time setup, and the part that receives them from visitors
socialpostiz, postiz-ghost-bridge, postiz-postgres, postiz-redis, postiz-temporal and its database and searchPostiz, the bridge that shares posts and collects the numbers, and Postiz's helpers
livetinyiceThe stream server
monitoringgrafana, prometheus, blackbox, cadvisor, node-exporter, grafana-ro-*The dashboards, the numbers behind them, the outside checks, and the jobs that give Grafana its read-only logins

The site

Normal on a first start, for a few minutes
Ghost waits until the analytics setup has written its tokens (kit.sh says it's waiting). On Kubernetes, Ghost, Grafana and the bridge show CreateContainerConfigError, secret "tinybird-tokens" not found, and pods sit in Init: until their database answers.
Everything says 403
The site only lets Cloudflare in (BEHIND_CLOUDFLARE=true). The DNS records must be proxied (the orange cloud). Visiting the server's own address directly, from home or a test, is turned away unless that address is in TRUSTED_EXTRA.
Certificate warnings that don't go away
Traefik's log says why: kit/kit.sh <folder> logs traefik | grep -i acme. With TLS_RESOLVER=le, Let's Encrypt must reach port 443 on this server, which it can't through Cloudflare's proxy: behind Cloudflare use cf. With cf, the usual cause is CLOUDFLARE_DNS_API_TOKEN in secrets/traefik.env (it needs Zone, DNS, Edit on the site's zone). Then start again.
"port is already allocated" when it starts
Another program on the machine has one of the kit's ports (80, 443, 8222). Stop it, or give the kit another port: HTTP_PORT, HTTPS_PORT or LIVE_PORT in site.env (Let's Encrypt's le needs 443 itself), then start again. sudo lsof -iTCP:<port> -sTCP:LISTEN says who has it.
"a container named traefik (or postiz...) is already on this machine"
The kit runs one site per Docker host, and some of its containers have fixed names. Another stack (or another kit site) has that one: stop or rename it first.
http:// or www. gives 404
They go to https://<your site> when the site has certificates (TLS_RESOLVER cf, le or self) and HTTPS_REDIRECT isn't false. www. also needs its DNS record pointed here.
Cloudflare shows 521 or 522
Cloudflare can't reach the server: the DNS record's address, ports 80 and 443 forwarded to it, Traefik running.
Ghost won't start: "Migration lock was never released"
Ghost was stopped while it was updating its database. If nothing else is running Ghost on that database, release the lock and start it again: 
kit/kit.sh kit/sites/mysite exec -T db sh -c \
  'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" ghost -e "UPDATE migrations_lock SET locked=0 WHERE lock_key=\"km01\""'
kit/kit.sh kit/sites/mysite restart ghost
If it then complains about the database itself, put the backup from before the update back.
No mail from Ghost (no sign-in codes, no members' links)
Ghost's mail settings: the mail part of data/ghost/ghost/config.production.json on Compose (then up -d --force-recreate ghost), secrets/ghost-mail.env on Kubernetes. Ghost's log shows the mail service's answer when you ask for a code.
No visitor numbers in Ghost's Analytics
analytics in MODULES, and tinybird-local and traffic-analytics running? Ad blockers hide some visitors.

Social

A post wasn't shared
The bridge's log: kit/kit.sh <folder> logs --tail 200 postiz-ghost-bridge. "Rejected request: bad or missing X-Ghost-Signature" means the secret in Ghost's webhook isn't GHOST_WEBHOOK_SECRET. No line at all means Ghost didn't call it: the webhook's address and event (Post published) in Ghost's integration. A post tagged #nosocial, or a members-only one (ONLY_PUBLIC, on by default), is skipped on purpose.
The bridge is up but Postiz refuses it
POSTIZ_API_KEY in secrets/postiz.env is Postiz's current key (Postiz's settings), and the network is connected in Postiz. Postiz allows 30 new posts an hour through its API; each Ghost post uses up to four.
Instagram or TikTok drafts don't arrive on the phone
The ntfy app is subscribed to NTFY_TOPIC on NTFY_URL. Send a test from the bridge:
kit/kit.sh kit/sites/mysite exec postiz-ghost-bridge sh -c 'wget -qO- --post-data test "$NTFY_URL/$NTFY_TOPIC"'
A network shows as an alert error in Grafana
It's in NETWORKS but its keys aren't set yet. Set them up, or take it out of NETWORKS.

Live

The streaming software can't connect
Behind Cloudflare, stream to the server's own address, not the site's name: Cloudflare doesn't pass port 8222. Port 8222 forwarded to the server, mount /stream-ogg, user source, TINYICE_SOURCE_PASSWORD, format Ogg.
Streaming, but no LIVE NOW bar
The theme's Live stream URL must be set (https://live.<your site>/stream-mp3). https://live.<your site>/live-status.json lists the stream while you're on.

Kubernetes

ImagePullBackOff
"not found" with the kit's own images: your copy is newer than the last release (between a change and its release), or k8s/images/built.env names a registry you no longer use: delete that file to use the release's images, or build again for yours. Only for images you build yourself: "no match for platform" means they weren't built for the nodes' kind (--platform), "unauthorized" that the nodes can't read your registry.
Pods Pending for long
"unbound PersistentVolumeClaims": no default StorageClass (kubectl get sc). "Insufficient memory": the nodes are full: add one.
A pod that keeps crashing doesn't come back after a fix
Databases and the analytics run as StatefulSets, which wait for the broken pod before using the new settings. Delete that pod: kubectl -n mysite delete pod <pod>.
A migration script stopped with exit code 3
A count differed between the two sides, marked DIFFERENT in its output. The DNS hasn't moved, so the old side is still the site. Calling it off: start its social part again (kit/kit.sh <folder> up -d on Compose, up.sh on Kubernetes).
"The cluster's Ghost is older" (or the other side's)
The database can't go to an older Ghost. Each side runs the Ghost version its copy of the kit names: bring the older side's kit up to the same version (git pull), then start it again there (kit/kit.sh <folder> up -d, or k8s/up.sh) and run the script again.
