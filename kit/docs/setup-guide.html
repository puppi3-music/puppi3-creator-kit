Before you start

Compose or Kubernetes

The kit runs the same site two ways. Pick one; a site can move from one to the other later with its data (the operations guide covers moving).

  • Docker Compose: one machine (a home server, a NAS, a rented server). The simplest, and the one to start with.
  • Kubernetes: a cluster you have, or one in Amazon's or Google's cloud for a busy stretch. More moving parts and, in a cloud, a monthly bill.

What you need

Three parts: what every site needs, what the way you run it needs (Compose or Kubernetes, only the one you pick), and what each optional part needs, only if you turn it on.

Every site. A domain whose DNS you control; the kit itself (git clone https://github.com/puppi3-music/puppi3-creator-kit.git, or the ZIP from GitHub); Python 3; an email address (Let's Encrypt writes to it about your certificates). Nothing to build: the kit's own images and its theme come ready-made with each release (to change the theme yourself: zip, unzip, and Node.js for its check).

Where it runs: pick one.

Run onWhat you need
Docker ComposeDocker with Compose 2.24 or newer, on a machine running Linux, macOS or Windows (inside WSL2, with the kit in WSL's own folders rather than on the Windows drive), Intel/AMD or ARM, that ports 80 and 443 reach from the internet (and 8222, with the live module, for your streaming software). Those are the only ports it opens to others (Temporal's admin page, with social, is on 127.0.0.1:8233, this machine only); one that's taken can be another (HTTP_PORT, HTTPS_PORT, LIVE_PORT in site.env; Let's Encrypt's le needs 443 itself). One kit site per Docker host: its Traefik takes the web ports, and some of its containers have fixed names (traefik, tinyice, postiz...), so kit.sh stops if another container already has one.
Kuberneteskubectl pointed at the cluster, a default StorageClass, a way for a Service of type LoadBalancer to get an outside address, and a way for its nodes to reach GitHub's registry (ghcr.io) for the kit's own images (which overlay says which kinds of cluster)

The optional parts. Besides the site itself (Ghost, its database and Traefik, always on), the kit has four parts, called modules, that you turn on or off. Setup asks which you want; each name below is what goes in MODULES.

How big a machine

In short: with every module on, 8 GB of memory for most sites (12 GB for a large one, about 20,000 page views a day) and 50 GB of free disk. The site alone, with no modules, runs in 2 GB. The measurements behind those numbers follow.

By site size. With every module on, pick by how busy the site is (measured on a Mac with 16 GB for Docker, kit 1.3.1, with a year of made-up page views in the analytics). Everything but the analytics stays the same size whatever the site's size. The analytics module keeps every page view in Tinybird, a database that Ghost Admin's Analytics reads; Tinybird holds more while it reads a long history, and that's what grows:

The highest numbers are short jumps (gone by the next sample, 30 s later: Tinybird taking in new page views or answering a query), so a run catches some and misses others: they're rounded up here. Between them, Tinybird holds 2 GB to 2.5 GB for a small or medium site and about 3 GB for a large one. The large site's highest jumps reached 5.8 GB and 8.6 GB in two runs; with the rest of the site that's 9 GB to 10 GB.

Where it goes, by module. Turning a module off saves its row. Measured on the kit's test site (Docker Desktop on a Mac, kit 1.3.1) with every module on, at rest, and ("when busy") while it streams, takes page hits and makes social previews. Page traffic barely moves it: most of it is held from the start. What does move it is the analytics history, above.

  • Memory: the site alone runs on a 2 GB machine, however busy. With everything on, it depends on the site's size (above): 8 GB for a small or medium site, 12 GB for a large one, plus what the machine's own system needs. On a Mac or Windows, Docker Desktop runs everything inside its own machine: give it that much under Settings, Resources (its default is often 8 GB: enough for a small or medium site, too tight for a large one). Anything else in Docker, a test cluster say, needs room on top.
  • Disk: about 1 GB for the site's folder at the start, plus the images above. It grows with what you upload (images, audio, video: usually the most), Prometheus's history (a year, at most 10 GB: then it drops the oldest), Tinybird's page hits and Postiz's uploads (small). Each container's log stops at 50 MB (the oldest lines go). 50 GB free covers everything for a long time.
  • Kubernetes: each pod asks for less than this and may use up to its limit (Tinybird 2 GiB, up to 4 GiB); two nodes of 4 CPUs and 16 GB hold everything, which is what the cluster recipes make.

How busy a site one machine holds (measured on a Mac with 16 GB for Docker, kit 1.2.3, with no Cloudflare cache in front, so every page view reached Ghost):

  • Visitors: 20 page views a second, about 1.7 million a day, with everything on. Ghost used 0.3 GB and pages took under 0.1 s; the whole site took about 0.9 GB more than at rest. That's far more than most creators' sites see, so a busy day doesn't need a bigger machine, or Kubernetes.
  • A large site's year of analytics: with a year of 20,000 page views a day (7.3 to 7.7 million), the 12-month and all-time views stopped with an error: each of Tinybird's queries may use 2 GB, and those need a little more. (Tinybird as a whole may use more than 2 GB: the 2 GB is per query.) That limit is Tinybird's own, the same on any machine and on Kubernetes, so more memory doesn't change it. A site that busy reads its year in shorter ranges.
  • Disk for the analytics: 1.2 GB to 1.9 GB for a large site's year (7.3 to 7.7 million page views).

Cloudflare or not

The kit works with or without Cloudflare in front of the site.

  • Behind Cloudflare (BEHIND_CLOUDFLARE=true, the default): DNS records proxied (the orange cloud). Only Cloudflare's addresses get through; anyone else gets 403. Visitors' real addresses and countries still reach the analytics. Your server's own address stays hidden. Certificates come from Let's Encrypt through Cloudflare's DNS (TLS_RESOLVER=cf, setup's choice here): put a Cloudflare API token that may edit the site's DNS (Zone, DNS, Edit) in CLOUDFLARE_DNS_API_TOKEN in secrets/traefik.env before the first start. It works even before anything outside reaches the server. (le can't work here: Let's Encrypt's check on port 443 would reach Cloudflare, not your server.) In Cloudflare, set the SSL mode to Full (strict): the server has a real certificate. To let your home network in directly as well, put its range in TRUSTED_EXTRA.
  • Without (BEHIND_CLOUDFLARE=false): plain DNS records to your server, open to everyone, certificates from Let's Encrypt (le).

The site's folder

A site is one folder. It holds everything that makes it that site, so back it up, and keep it private: it has the passwords. kit/sites/ is kept out of git, so it's a good place for it.

kit/setup.sh kit/sites/mysite

What it makes

  • site.env: your answers, and every other setting explained, including how posts are shared (which networks, which go out by themselves, the tags you use in Ghost). Read it once.
  • secrets/: one file per part, with random passwords filled in and a comment on each line. The keys from outside services go here later.
  • data/: everything the site keeps (databases, images, Grafana, the stream server's settings), with the config files the parts need to start.

Inside, each part has its folder and its secrets file by its name in the kit: traefik, postiz (Postiz and the bridge), icecast (the stream server), monitoring, and ghost, Ghost and its database (a site made before kit 1.2.0 has it as puppi3, the name of the site the kit came from, and keeps it).

Running setup again on the same folder keeps what's there and only adds what's missing. Every setting, its default and which file it's in: the Settings reference.

On Linux

Setup asks for sudo once to give each part its folders: the stream server, Prometheus, Grafana and the database (MySQL) each run as their own user, and can't write to a folder that's yours.

Docker Compose

DNS first

A try-out has no DNS yet: skip this, start it, and reach it as Trying it at home first says.

Point these names at the server (proxied, if behind Cloudflare). Setup printed the list for your modules:

  • the site, and www. (the kit sends visitors from www. and http:// on to https:// and the site's own name)
  • live. (with live), for listeners. Cloudflare doesn't pass port 8222, so behind Cloudflare your streaming software connects to the server's own address instead (Live).
  • postiz. (with social)
  • grafana. (with monitoring), if you want it outside home

Start it

kit/kit.sh kit/sites/mysite up -d

The first start downloads the images and sets up the analytics, a few minutes in all. kit.sh takes any docker compose command after the folder:

kit/kit.sh kit/sites/mysite ps            # what's running
kit/kit.sh kit/sites/mysite logs -f ghost # one part's log
kit/kit.sh kit/sites/mysite down          # stop it (the data stays)

Open https://<your site>/: Ghost's own front page (its default theme, with a sample post) means it works. Then finish by hand.

If it stops with port is already allocated, something else on the machine has that port: stop it, or give the kit another one (HTTP_PORT, HTTPS_PORT, LIVE_PORT in site.env) and start again.

The home-network-only names

Traefik's dashboard, TinyIce's admin and Grafana also answer at traefik., tinyice. and grafana.<home domain>, over plain http, to private addresses only: the ranges in data/traefik/dynamic/lan-only.yml, your site's own file. Set them to your home network's (or your VPN's); Traefik picks up a change at once.

  • Leave out Docker's own networks (172.16.0.0/12, by default). Docker hands some connections over itself, such as any over IPv6 on a server that has an IPv6 address, and those arrive from its network's gateway, an address in that range. With it in the file, anyone could reach these pages. Setup leaves it out; a site made before kit 1.2.3 has it, and kit.sh warns at every start until you take it out.
  • On Docker Desktop (a Mac, Windows) every connection looks like it comes from 192.168.65.1, so the file can't tell home from anywhere else: these pages answer anyone who can reach the computer. That's fine on a computer at home; don't forward ports 80 and 443 to it from your router. kit.sh says so at each start.
  • If these pages answer "Forbidden" on Docker Desktop even from the computer itself, its proxy and monitoring networks have gone stale: connections arrive from a network's gateway instead of 192.168.65.1, and the file rightly leaves that out. kit.sh checks after each start and warns. To fix it, stop the site (kit/kit.sh <folder> down), remove the two networks (docker network rm proxy monitoring; kit.sh makes them again), and start it.

On Kubernetes the load balancer keeps the visitor's address, so the private ranges there are home only.

Trying it at home first

You can run the whole site on your own computer before your domain points anywhere, to look around. Answer yes to setup's first question. Then:

  • Reaching it: your browser needs to find the site's names on your computer. Add a line to your hosts file (/etc/hosts on Linux or a Mac; on Windows C:\Windows\System32\drivers\etc\hosts, opened as administrator, since the browser runs in Windows, not in WSL) with every name setup listed, such as 127.0.0.1 example.com www.example.com live.example.com postiz.example.com grafana.example.com. The home-network names (grafana.localhost and the like) need nothing: browsers send *.localhost to your own machine. The browser warns about the certificate once (it's Traefik's own, not a real one). From a terminal: curl -k --resolve example.com:443:127.0.0.1 https://example.com/.
  • What works: Ghost and its admin (setup turns off its sign-in codes by email for a try-out, as there's no mail service yet; turn them back on with the real thing: Mail first), the theme, the short links, the analytics (your own visits are counted), Grafana, Postiz and its sign-up.
  • What waits for the real thing: certificates from Let's Encrypt, Ghost's webhook to the bridge (Ghost sends it only to a public address), the networks' sign-ins, and your phone's alerts. Grafana's public checks can't reach a name only your computer knows, so Health shows the site, Ghost's backend, the live stream and the certificate as down or empty, and the alerts for them ("… is down", "Ghost isn't answering", "Live stream server is down") fire in Grafana (not on your phone: a try-out has no notifications). That's expected.

When the domain is ready, the try-out becomes the real site:

  1. Point the domain's names at the server (DNS first), and take the try-out's line out of your hosts file.
  2. In site.env: BEHIND_CLOUDFLARE (whether only Cloudflare reaches the site) and TLS_RESOLVER (cf or le, for real certificates): Cloudflare or not. And NTFY_URL for phone notifications (https://ntfy.sh, or your own server).
  3. In secrets/traefik.env: your own address in ACME_EMAIL (setup put admin@<your site> there for the try-out), and with cf the Cloudflare token in CLOUDFLARE_DNS_API_TOKEN.
  4. Give Ghost its mail (secrets/ghost-mail.env: Mail first), then turn its sign-in codes back on: staffDeviceVerification to true in data/ghost/ghost/config.production.json.
  5. Start again, then make Ghost read its changed file: 
    kit/kit.sh <folder> up -d
kit/kit.sh <folder> up -d --force-recreate ghost

To try it and keep nothing: kit/kit.sh <folder> down -v, then delete the folder (sudo rm -rf on Linux, where the parts own their folders). Docker keeps what it downloaded (several GB of images) and a few unnamed volumes; to free that space too:

docker volume rm $(docker volume ls -q --filter label=com.docker.compose.project=<short name>)
docker image rm ghcr.io/puppi3-music/puppi3-creator-kit/{ghost-bridge,tb-setup}:$(cat kit/VERSION)
docker image prune -a      # every image no container uses: also other projects' (it asks first)

Finish by hand

What only you can do, in this order. Setup printed a short version of this list with your names in it. On Kubernetes it's the same, except where it says so.

Ghost

  1. Mail first. Ghost emails staff a code each time they sign in on a new device, and members their sign-in links. Its own way of sending rarely arrives, so give it a mail service (any with SMTP). Copy kit/examples/ghost-mail.env.example to secrets/ghost-mail.env and fill it in (its settings, Ghost's docs), then start again: kit/kit.sh <folder> up -d (Ghost restarts, a few seconds without the site) or k8s/up.sh <folder> <overlay>. Not in config.production.json: everyone on the machine can read that file, and only you can read secrets/.
  2. Make the owner account at https://<your site>/ghost/, then set Ghost's own time zone (Settings → Timezone, under General settings) to the site's: Ghost keeps its own, for its dates and its scheduled posts.
  3. The theme: download puppi3-creator-kit-theme.zip from the kit's release for your version (kit/VERSION; changed the theme? kit/theme-zip.sh builds it, in kit/dist/). Upload it in Settings → Theme → Change theme → Upload theme, then Activate. With live, set the theme's Live stream URL (Settings → Design & branding → Customize, the Theme tab) to https://live.<your site>/stream-mp3: the LIVE NOW bar shows only once it's set. The theme's other settings, links to your other platforms in the footer and the short links: the Theme guide.
  4. Short links: upload kit/redirects.yaml in Settings → Labs (under Advanced) → Open → Beta features → Redirects → Upload redirects file (the bio links like /ig, and the tagged links the bridge posts).

Social

  1. Make your account at https://postiz.<your site>, then close sign-ups: POSTIZ_DISABLE_REGISTRATION=true in secrets/postiz.env.
  2. Make each network's app, put its keys in secrets/postiz.env, start again, and connect the networks in Postiz: the Networks guide has each one step by step, with the traps on the way.
  3. Copy Postiz's API key (in Postiz, Settings → Developers → Public API) into POSTIZ_API_KEY in secrets/postiz.env.
  4. In Ghost, Settings → Integrations (under Advanced) → Custom → Add custom integration. Its Admin API key goes in GHOST_ADMIN_API_KEY in secrets/postiz.env (the Social preview button, and the site's own numbers on the dashboards). Give it a webhook: event Post published, address https://postiz.<your site>/ghost-webhook, secret = GHOST_WEBHOOK_SECRET from secrets/postiz.env. Ghost sends it only to a public address: postiz.<your site> must resolve to one from the server (so not a home-network address, even if your home DNS gives one).
  5. To see what it would post before anything goes out: GHOST_BRIDGE_DRY_RUN=true in secrets/postiz.env. The bridge then posts nothing, and logs and previews what it would; set it back to false when you're happy. While it's on, it sends no phone notifications either.
  6. If you use the manual drafts (the default for Instagram and TikTok), make a tag called Post in app once in Postiz's post editor, or change DRAFT_TAG in site.env.
  7. Start again (kit/kit.sh <folder> up -d or k8s/up.sh <folder> <overlay>), then publish a test post with the internal tag #nosocial to see that nothing goes out, and a real one when you're ready.

Whoever posts: the Posting guide. How posts are shared (which networks, what posts by itself, the tags) is set in site.env; the defaults post Bluesky and Threads by themselves and make Instagram and TikTok drafts with a phone notification for each. For TikTok photo posts that go out by themselves (#autopost on a post with no video or audio), TikTok fetches the photos from Postiz: verify https://postiz.<your site>/ as a URL prefix in TikTok's developer portal.

Numbers from each network

The bridge collects each network's numbers for the dashboards, every hour, for the networks in NETWORKS. Most need nothing more than the channel connected in Postiz. Your site's own numbers need the Admin API key from the Social step above, SoundCloud an app of the bridge's own, Bluesky and Mixcloud only your profile, and Google Search and Cloudflare a key each (those two aren't in NETWORKS: their numbers appear once their keys are there). The Networks guide has each one step by step. Start again after adding a key. Until a network in NETWORKS has what it needs, it shows as an alert error, and the Networks not shown box at the bottom of the Platforms dashboard says what's missing. Reading the numbers: the Analytics guide.

Phone notifications

In the ntfy app, subscribe to the topic in NTFY_TOPIC (secrets/postiz.env) on your ntfy server. Setup made up a long random one: on ntfy.sh anyone who knows a topic can read it, so keep it unguessable. The alerts use the same topic.

Live

In your streaming software, an Icecast stream: server live.<your site>, or the server's own address when the site is behind Cloudflare (which doesn't pass this port), port 8222 (or your LIVE_PORT), mount /stream-ogg, user source, password TINYICE_SOURCE_PASSWORD from secrets/icecast.env, format Ogg (Vorbis or Opus, either works). It goes straight to the stream server, not through Traefik (which would drop the audio). On Kubernetes, port 8222 is the tinyice-source Service's own outside address.

That port is all of TinyIce, its admin sign-in too, and it's plain http: when you stream from away, the source password crosses the internet unencrypted, and anyone who catches it could stream on your site. So keep the port to the addresses you stream from:

  • A firewall rule on the server (or your cloud's) that lets only your own addresses reach port 8222 (your LIVE_PORT).
  • On Compose, LIVE_BIND in site.env makes it listen on one of the server's addresses only: 127.0.0.1 when the streaming software runs on the same machine, a home-network or VPN address to stream only from there.
  • On Kubernetes, LIVE_SOURCE_RANGES in site.env (comma-separated ranges, like 203.0.113.7/32) is all its load balancer lets in.

Then start again. Listeners aren't affected: they come through https://live.<your site>, not this port.

TinyIce's admin page is http://tinyice.<home domain>, from home (the home-network-only names), with TINYICE_ADMIN_USER and TINYICE_ADMIN_PASSWORD.

Grafana

https://grafana.<your site>, or http://grafana.<home domain> at home: user admin, password GRAFANA_ADMIN_PASSWORD in secrets/monitoring.env. For someone who only reads the numbers (the site's owner, say), make an account of their own instead of sharing that one: Administration → Users and access → Users → New user (a new account can look, not change). The dashboards are made for your site each time the site starts, so changes made in Grafana don't stay. A network in NETWORKS that isn't set up yet shows as an alert error until you set it up or take it out. Reading the dashboards: the Analytics guide.

Kubernetes

The same folder runs on a cluster with k8s/up.sh. It turns site.env and secrets/ into the cluster's settings, applies everything into a namespace named after the short name, and waits until every part is ready, stopping early with the reason if one is stuck.

The images

Three of the images are the kit's own (the analytics setup job, the stream relay, the bridge); the rest come from Docker Hub. Traefik is Traefik's own image, with the kit's two plugins handed to it as a ConfigMap. Each release publishes the kit's for Intel/AMD and ARM, at ghcr.io/puppi3-music/puppi3-creator-kit/<name>:<version>, and up.sh uses those for your version (kit/VERSION): nothing to build.

Changed one of them (the bridge's code, say), or want them in a registry of your own? Build and push them there; up.sh then uses those instead, for every site and cluster, until you delete k8s/images/built.env (the Kubernetes tests leave one too):

docker login <registry>
k8s/build-images.sh --registry <registry>/creator-kit --platform linux/amd64   # linux/arm64 for ARM nodes; both, comma-separated

Up

k8s/up.sh kit/sites/mysite selfhosted --render   # only writes what it would apply: data/k8s/rendered.yaml
UP_TIMEOUT=1200 k8s/up.sh kit/sites/mysite selfhosted   # the first time: 20 minutes to be ready, not 5

It names the cluster kubectl points at and asks before using it. The first time takes a while (image downloads, the analytics' first start), hence the longer wait (UP_TIMEOUT, in seconds; later runs need no more than the usual 5 minutes). Ghost, traffic-analytics, Grafana and the bridge wait with CreateContainerConfigError until the analytics setup job has made its tokens: that's normal.

Then the outside addresses, for DNS:

kubectl -n <short name> get svc traefik tinyice-source    # EXTERNAL-IP

Point the site's names at traefik's address and the streaming software at tinyice-source's, then finish by hand as on Compose. On EKS each address is a name (ending in elb.amazonaws.com), not a number: point the site's names at it with CNAME records (Cloudflare takes one for the bare domain too). k8s/up.sh <folder> <overlay> --down deletes the site from the cluster, volumes and all (name the overlay: without one it means local, the throwaway test cluster).

EKS or GKE

A cloud site needs a few things made once with the cloud's own tools: the cluster, the databases (Ghost's MySQL, and Postgres for Postiz with social), and a private bucket for Ghost's images and files (a registry only if you build the kit's images yourself: the images). Their addresses go in cloud-eks.env or cloud-gke.env in the site's folder; the comments in each overlay's example say what each line is. The cloud costs money for as long as these exist, so tear them down when you're done: the cluster with eksctl delete cluster -f k8s/clusters/eks.yaml or PROJECT=<project> REGION=<region> k8s/clusters/gke.sh down, the databases and bucket in the cloud's console. The Cloud guide has each step with its commands, what it costs, and the whole of a busy stretch in a cloud: moving a running site there and back.

Amazon EKS

  • Cluster: eksctl create cluster -f k8s/clusters/eks.yaml (check its name, region and node size first), then kubectl apply -f k8s/clusters/eks-gp3.yaml and the AWS Load Balancer Controller, with the ServiceAccount the cluster file made: 
    helm repo add eks https://aws.github.io/eks-charts
helm install aws-load-balancer-controller eks/aws-load-balancer-controller -n kube-system \
  --set clusterName=<the cluster's name> --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller
  • Databases: RDS for MySQL 8 and RDS for Postgres 17 in the cluster's network, on its private subnets, reachable only from the nodes' security group. Postgres's parameter group needs rds.force_ssl=0 (Postiz connects without TLS; the traffic stays in the network).
  • Bucket: a private S3 bucket, and an IAM role for ServiceAccount ghost in your namespace (IRSA) that may read, write and delete its objects and list it. No key is stored anywhere.
  • Registry, only for images you build yourself: ECR repositories creator-kit/tb-setup, creator-kit/icecast-relay and creator-kit/ghost-bridge.

Then cp k8s/overlays/eks/cloud.env.example <folder>/cloud-eks.env and fill it in.

Google GKE

  • Cluster: PROJECT=<project> REGION=<region> k8s/clusters/gke.sh up (one zone, two nodes, Workload Identity on).
  • Databases: Cloud SQL for MySQL 8 and for Postgres 17, and a Google service account with the Cloud SQL Client role, tied to Kubernetes ServiceAccount cloud-sql in your namespace (gke.sh up prints the command that ties them). Pods reach the databases through the Cloud SQL Auth Proxy beside them.
  • Bucket: a private Cloud Storage bucket, a service account that may use only it, and an HMAC key for it (Ghost uses Cloud Storage's S3-compatible side).
  • Registry, only for images you build yourself: an Artifact Registry Docker repository.

Then cp k8s/overlays/gke/cloud.env.example <folder>/cloud-gke.env and fill it in.

The site's secrets for a cloud

  • secrets/ghost.env (secrets/puppi3.env in a site made before kit 1.2.0): Ghost's login on the cloud's MySQL (its master user and password, and the database's name).
  • secrets/cloud.env: Postgres's master login (POSTGRES_MASTER_USER, POSTGRES_MASTER_PASSWORD); a job makes Postiz's own logins with it.
  • secrets/s3.env (GKE only): the HMAC key.
  • secrets/ghost-mail.env: Ghost's mail.

Setup already made secrets/ghost.env and you made secrets/ghost-mail.env: change only the login in the first. cloud.env and s3.env start from their examples in k8s/examples/. The Settings reference lists every line. Then look at what it would apply, k8s/up.sh <folder> eks --render (or gke), and run the same without --render. The kit's images come from the release here too (the images).

Test before the DNS

Before pointing the domain at the cloud, check the site through the cluster's own address. Behind Cloudflare only Cloudflare gets in, so let yourself in first: your own internet address in TRUSTED_EXTRA (like 203.0.113.7/32), then k8s/up.sh again. Then:

curl -k --connect-to example.com:443:<traefik's EXTERNAL-IP>:443 -sI https://example.com/

For a browser, add a hosts-file line with that address and the site's names, as for the try-out (on EKS, dig +short <the name> gives its addresses). Sign in to Ghost Admin and upload a picture to a draft: if it shows, Ghost can reach the bucket. Once the DNS points at the cloud, take the hosts-file line out, and your address out of TRUSTED_EXTRA (then k8s/up.sh again).

Checking that the kit works

For whoever changes the kit (to try it for your own site, use the try-out instead): on your own computer, the kit can build a throwaway site, check every part end to end, then remove it. It never touches a real site. The Compose test runs on Linux, a Mac or Windows inside WSL2; the Kubernetes ones, for now, only on a Mac with Docker Desktop.

kit/test.sh                               # Compose: the site kit.test
k8s/test/test.sh                          # Kubernetes, on a k3d cluster it makes (local overlay)
k8s/test/test.sh --overlay k3d-eks        # the eks overlay, with stand-ins for RDS and S3
k8s/test/test.sh --overlay k3d-gke        # the gke overlay, with stand-ins for Cloud SQL and Cloud Storage
k8s/test/test.sh --render-only            # every overlay rendered and checked, no cluster (a minute)

The Compose test needs ports 80, 443, 8222 free (LIVE_PORT=<another> kit/test.sh for the stream's), ffmpeg, Python 3, Node.js 20 or newer and a browser for it (npm install and npx playwright install --with-deps chromium in kit/theme-test/); it says what's missing; the Kubernetes ones also need k3d, kubeconform, ports 9080, 9443, 8222 and 5111 free, and 12 GB of memory for Docker. --keep leaves the site up to look around. A Kubernetes test that makes its cluster downloads every image first, so it gives the site 15 minutes to be ready instead of 5. The Kubernetes tests build the kit's images into their cluster's registry and leave k8s/images/built.env naming it: delete that file before running a real site with k8s/up.sh (the images).

Changing things later

  • A setting: edit site.env or a file in secrets/, then start again (kit/kit.sh <folder> up -d, or k8s/up.sh <folder> <overlay>). Only the parts that use it restart.
  • A module: change MODULES and start again. A module switched off has its alerts taken out of Grafana too. Switching live on later needs only its DNS name and the theme's Live stream URL: its passwords were made at setup.
  • Phone notifications: NTFY_URL in site.env is the one place for both the bridge and Grafana's alerts (empty = none); start again and kit.sh restarts Grafana for it.
  • A network: change NETWORKS (the dashboards' sections and the bridge's collectors) and, for one you post to, CHANNELS (where posts go, in Postiz's names: bluesky, threads, instagram-standalone, tiktok, tiktok-business), then start again. What its numbers need: Numbers from each network.
