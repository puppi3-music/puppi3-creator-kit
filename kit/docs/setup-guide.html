Before you start

Compose or Kubernetes

The kit runs the same site two ways. Pick one; a site can move from one to the other later with its data (the operations guide covers moving).

  • Docker Compose: one machine (a home server, a NAS, a rented server). The simplest, and the one to start with.
  • Kubernetes: a cluster you have, or one in Amazon's or Google's cloud for a busy stretch. More moving parts and, in a cloud, a monthly bill.

What you need

ForWhat
EveryoneA domain whose DNS you control; the kit itself (git clone https://github.com/puppi3-music/puppi3-creator-kit.git, or the ZIP from GitHub); Python 3; an email address (Let's Encrypt writes to it about your certificates). Nothing to build: the kit's own images and its theme come ready-made with each release (to change the theme yourself: zip, unzip, and Node.js for its check)
ComposeDocker with Compose 2.24 or newer, on a machine running Linux, macOS or Windows (inside WSL2, with the kit in WSL's own folders rather than on the Windows drive), Intel/AMD or ARM, that ports 80 and 443 reach from the internet (and 8222, with the live module, for your streaming software). Those are the only ports it opens to others (Temporal's admin page, with social, is on 127.0.0.1:8233, this machine only); one that's taken can be another (HTTP_PORT, HTTPS_PORT, LIVE_PORT in site.env; Let's Encrypt's le needs 443 itself). One kit site per Docker host: its Traefik takes the web ports, and some of its containers have fixed names (traefik, tinyice, postiz...), so kit.sh stops if another container already has one.
Kuberneteskubectl pointed at the cluster, a default StorageClass, a way for a Service of type LoadBalancer to get an outside address, and a way for its nodes to reach GitHub's registry (ghcr.io) for the kit's own images
socialA developer app for each network you post to (Postiz's docs say how for each one); later, optional keys for SoundCloud, Cloudflare and Search Console numbers
liveSoftware that streams Ogg to an Icecast server (butt, Mixxx, ffmpeg and most broadcasting and DJ apps do)
Phone notificationsThe ntfy app; ntfy.sh works, or your own ntfy server

How big a machine

Measured on the kit's test site (Docker Desktop on a Mac, kit 1.2.0; analytics kit 1.2.2) with every module on, at rest and while it streams, takes page hits and makes social previews. Memory barely moves between the two: most of it is held from the start.

  • Memory: the site alone runs on a 2 GB machine. With everything on, 10 GB at least, 12 to 16 GB to be comfortable, plus what the machine's own system needs. On a Mac or Windows, Docker Desktop runs everything inside its own machine: give it that much under Settings, Resources (its default is often 8 GB, too tight with every module on).
  • Disk: about 1 GB for the site's folder at the start, plus the images above. It grows with what you upload (images, audio, video: usually the most), Prometheus's history (a year, at most 10 GB: then it drops the oldest), Tinybird's page hits and Postiz's uploads (small). 50 GB free covers everything for a long time.
  • Kubernetes: each pod asks for less than this and may use up to its limit (Tinybird 2 GiB, up to 4 GiB); two nodes of 4 CPUs and 16 GB hold everything, which is what the cluster recipes make.

Cloudflare or not

The kit works with or without Cloudflare in front of the site.

  • Behind Cloudflare (BEHIND_CLOUDFLARE=true, the default): DNS records proxied (the orange cloud). Only Cloudflare's addresses get through; anyone else gets 403. Visitors' real addresses and countries still reach the analytics. Your server's own address stays hidden. Certificates come from Let's Encrypt through Cloudflare's DNS (TLS_RESOLVER=cf, setup's choice here): put a Cloudflare API token that may edit the site's DNS (Zone, DNS, Edit) in CLOUDFLARE_DNS_API_TOKEN in secrets/traefik.env before the first start. It works even before anything outside reaches the server. (le can't work here: Let's Encrypt's check on port 443 would reach Cloudflare, not your server.)
  • Without (BEHIND_CLOUDFLARE=false): plain DNS records to your server, open to everyone, certificates from Let's Encrypt (le).

Set Cloudflare's SSL mode to Full (strict): the server has a real certificate either way. To let your home network in directly as well, put its range in TRUSTED_EXTRA.

The site's folder

A site is one folder. It holds everything that makes it that site, so back it up, and keep it private: it has the passwords. kit/sites/ is kept out of git, so it's a good place for it.

kit/setup.sh kit/sites/mysite

To answer without being asked (a script, a second site), give the values as variables and add --yes: SITE_HOST=example.com ID_PREFIX=ex kit/setup.sh kit/sites/ex --yes.

What it makes

  • site.env: your answers, and every other setting explained, including how posts are shared (which networks, which go out by themselves, the tags you use in Ghost). Read it once.
  • secrets/: one file per part, with random passwords filled in and a comment on each line. The keys from outside services go here later.
  • data/: everything the site keeps (databases, images, Grafana, the stream server's settings), with the config files the parts need to start.

Inside, each part has its folder and its secrets file by its name in the kit: traefik, postiz (Postiz and the bridge), icecast (the stream server), monitoring, and ghost, Ghost and its database (a site made before kit 1.2.0 has it as puppi3, the name of the site the kit came from, and keeps it).

Running setup again on the same folder keeps what's there and only adds what's missing. Every setting, its default and which file it's in: the Settings reference.

Docker Compose

DNS first

Point these names at the server (proxied, if behind Cloudflare). Setup printed the list for your modules:

  • the site, and www. (which goes to the site; so does http://, to https://)
  • live. (with live), for listeners. Cloudflare doesn't pass port 8222, so behind Cloudflare your streaming software connects to the server's own address instead (Live).
  • postiz. (with social)
  • grafana. (with monitoring), if you want it outside home

Start it

kit/kit.sh kit/sites/mysite up -d

The first start downloads the images and sets up the analytics, a few minutes in all. kit.sh takes any docker compose command after the folder:

kit/kit.sh kit/sites/mysite ps            # what's running
kit/kit.sh kit/sites/mysite logs -f ghost # one part's log
kit/kit.sh kit/sites/mysite down          # stop it (the data stays)

Open https://<your site>/: Ghost's welcome page means it works. Then finish by hand.

On Linux

Setup asks for sudo once to give each part its folders: the stream server, Prometheus, Grafana, the database (MySQL) and Postiz's search engine each run as their own user, and can't write to a folder that's yours.

If it stops with port is already allocated, something else on the machine has that port: stop it, or give the kit another one (HTTP_PORT, HTTPS_PORT, LIVE_PORT in site.env) and start again.

Trying it at home first

You can run the whole site on your own computer before your domain points anywhere, to look around. Answer yes to setup's first question. Then:

  • Reaching it: your browser needs to find the site's names on your computer. Add a line to your hosts file (/etc/hosts on a Mac or Linux) with every name setup listed, such as 127.0.0.1 example.com www.example.com live.example.com postiz.example.com grafana.example.com. The home-network names (grafana.localhost and the like) need nothing: browsers send *.localhost to your own machine. The browser warns about the certificate once (it's Traefik's own, not a real one). From a terminal: curl -k --resolve example.com:443:127.0.0.1 https://example.com/.
  • What works: Ghost and its admin (setup turns off its sign-in codes by email for a try-out, as there's no mail service yet; turn them back on with the real thing: Mail first), the theme, the short links, the analytics (your own visits are counted), Grafana, Postiz and its sign-up.
  • What waits for the real thing: certificates from Let's Encrypt, Ghost's webhook to the bridge (Ghost sends it only to a public address), the networks' sign-ins, and your phone's alerts. Grafana's public checks can't reach a name only your computer knows, so Health shows the site, Ghost's backend, the live stream and the certificate as down or empty, and the "is down" and "Ghost isn't answering" alerts fire in Grafana (not on your phone: a try-out has no notifications). That's expected.

When the domain is ready: point its DNS here, set TLS_RESOLVER (and BEHIND_CLOUDFLARE) for the real certificates and NTFY_URL for phone alerts in site.env, give Ghost its mail and set staffDeviceVerification back to true in data/ghost/ghost/config.production.json, and start again (up -d --force-recreate ghost for Ghost's file).

To try it and keep nothing: kit/kit.sh <folder> down -v, then delete the folder. Docker keeps what it downloaded and built (several GB of images) and a few unnamed volumes; to free that space too:

docker volume rm $(docker volume ls -q --filter label=com.docker.compose.project=<short name>)
docker image rm ghcr.io/puppi3-music/puppi3-creator-kit/{ghost-bridge,tb-setup}:$(cat kit/VERSION)
docker image prune -a      # every image no container uses: also other projects' (it asks first)

Finish by hand

What only you can do, in this order. Setup printed the same list with your names in it. On Kubernetes it's the same, except where it says so.

Ghost

  1. Mail first. Ghost emails staff a code each time they sign in on a new device, and members their sign-in links. Its own way of sending rarely arrives, so give it a mail service (any with SMTP). On Compose: the mail part of data/ghost/ghost/config.production.json (Ghost's docs), then kit/kit.sh <folder> up -d --force-recreate ghost. On Kubernetes: secrets/ghost-mail.env (its settings).
  2. Make the owner account at https://<your site>/ghost/, then set Ghost's own time zone (Settings, General, Timezone) to the site's: Ghost keeps its own, for its dates and its scheduled posts.
  3. The theme: download puppi3-creator-kit-theme.zip from the kit's release for your version (kit/VERSION; changed the theme? kit/theme-zip.sh builds it, in kit/dist/). Upload it in Settings, Design & branding, Customize, Change theme, Upload theme, then Activate. With live, set the theme's Live stream URL (Design & branding, Customize, the Theme tab) to https://live.<your site>/stream-mp3: the LIVE NOW bar shows only once it's set. The theme's other settings, links to your other platforms in the footer and the short links: the Theme guide.
  4. Short links: upload kit/redirects.yaml in Settings, Labs (under Advanced: Open, Beta features), Redirects (the bio links like /ig, and the tagged links the bridge posts).

Social

  1. Make your account at https://postiz.<your site>, then close sign-ups: POSTIZ_DISABLE_REGISTRATION=true in secrets/postiz.env.
  2. Put each network's app keys in secrets/postiz.env, start again, and connect the networks in Postiz.
  3. In Postiz's settings, make an API key: POSTIZ_API_KEY.
  4. In Ghost, Settings, Integrations, the Custom tab, add a custom integration. Its Admin API key goes in GHOST_ADMIN_API_KEY (the Social preview button). Give it a webhook: event Post published, address https://postiz.<your site>/ghost-webhook, secret = GHOST_WEBHOOK_SECRET from secrets/postiz.env. Ghost sends it only to a public address: postiz.<your site> must resolve to one from the server (so not a home-network address, even if your home DNS gives one).
  5. To see what it would post before anything goes out: GHOST_BRIDGE_DRY_RUN=true in secrets/postiz.env. The bridge then posts nothing, and logs and previews what it would; set it back to false when you're happy. While it's on, its phone notifications are off too, unless you also set DRY_RUN_NTFY=true.
  6. If you use the manual drafts (the default for Instagram and TikTok), make a tag called Post in app once in Postiz's post editor, or change DRAFT_TAG in site.env.
  7. Start again (kit/kit.sh <folder> up -d or k8s/up.sh <folder> <overlay>), then publish a test post with the internal tag #nosocial to see that nothing goes out, and a real one when you're ready.

Whoever posts: the Posting guide. How posts are shared (which networks, what posts by itself, the tags) is set in site.env; the defaults post Bluesky and Threads by themselves and make Instagram and TikTok drafts with a phone notification for each.

Phone notifications

In the ntfy app, subscribe to the topic in NTFY_TOPIC (secrets/postiz.env) on your ntfy server. Setup made up a long random one: on ntfy.sh anyone who knows a topic can read it, so keep it unguessable. The alerts use the same topic.

Live

In your streaming software, an Icecast stream: server live.<your site>, or the server's own address when the site is behind Cloudflare (which doesn't pass this port), port 8222 (or your LIVE_PORT), mount /stream-ogg, user source, password TINYICE_SOURCE_PASSWORD from secrets/icecast.env, format Ogg (Vorbis or Opus, either works). It goes straight to the stream server, not through Traefik (which would drop the audio). On Kubernetes, port 8222 is the tinyice-source Service's own outside address.

TinyIce's admin page is http://tinyice.<home domain>, from home, with TINYICE_ADMIN_USER and TINYICE_ADMIN_PASSWORD.

Grafana

https://grafana.<your site>, or http://grafana.<home domain> at home: user admin, password GRAFANA_ADMIN_PASSWORD in secrets/monitoring.env. The dashboards are made for your site each time the site starts, so changes made in Grafana don't stay. A network in NETWORKS that isn't set up yet shows as an alert error until you set it up or take it out. Reading the dashboards: the Analytics guide.

Kubernetes

The same folder runs on a cluster with k8s/up.sh. It turns site.env and secrets/ into the cluster's settings, applies everything into a namespace named after the short name, and waits until every part is ready, stopping early with the reason if one is stuck.

Which overlay

OverlayFor
selfhostedAny cluster of your own: MySQL runs in the cluster, Ghost's files on a volume
eksAmazon EKS, with RDS databases and an S3 bucket (below)
gkeGoogle GKE Standard, with Cloud SQL and a Cloud Storage bucket (below)
local, k3d-eks, k3d-gkeNot for a real site: a throwaway cluster on your own machine, for trying things: k8s/test/k3d.sh up makes one (k3d, with a registry at localhost:5111), then k8s/build-images.sh --registry k3d and k8s/up.sh <folder> local

The images

Three of the images are the kit's own (the analytics setup job, the stream relay, the bridge); the rest come from Docker Hub. Traefik is Traefik's own image, with the kit's two plugins handed to it as a ConfigMap. Each release publishes the kit's for Intel/AMD and ARM, at ghcr.io/puppi3-music/puppi3-creator-kit/<name>:<version>, and up.sh uses those for your version (kit/VERSION): nothing to build.

Changed one of them (the bridge's code, say), or want them in a registry of your own? Build and push them there; up.sh then uses those instead, until you delete k8s/images/built.env:

docker login <registry>
k8s/build-images.sh --registry <registry>/creator-kit --platform linux/amd64   # linux/arm64 for ARM nodes; both, comma-separated

Up

k8s/up.sh kit/sites/mysite selfhosted --render   # only writes what it would apply: data/k8s/rendered.yaml
UP_TIMEOUT=1200 k8s/up.sh kit/sites/mysite selfhosted

It names the cluster kubectl points at and asks before using it. The first time takes a while (image downloads, the analytics' first start). Ghost, Grafana and the bridge wait with CreateContainerConfigError until the analytics setup job has made its tokens: that's normal.

Then the outside addresses, for DNS:

kubectl -n <short name> get svc traefik tinyice-source    # EXTERNAL-IP

Point the site's names at traefik's address and the streaming software at tinyice-source's, then finish by hand as on Compose. k8s/up.sh <folder> --down deletes the site from the cluster, volumes and all.

EKS or GKE

A cloud site needs a few things made once with the cloud's own tools: the cluster, the databases (Ghost's MySQL, and Postgres for Postiz with social), and a private bucket for Ghost's images and files (a registry only if you build the kit's images yourself: the images). Their addresses go in cloud-eks.env or cloud-gke.env in the site's folder; the comments in each overlay's example say what each line is. The cloud costs money for as long as these exist, so tear them down when you're done.

Amazon EKS

  • Cluster: eksctl create cluster -f k8s/clusters/eks.yaml (check its name, region and node size first), then kubectl apply -f k8s/clusters/eks-gp3.yaml and the AWS Load Balancer Controller (Helm chart eks/aws-load-balancer-controller, with the ServiceAccount the cluster file made).
  • Databases: RDS for MySQL 8 and RDS for Postgres 17 in the cluster's network, on its private subnets, reachable only from the nodes' security group. Postgres's parameter group needs rds.force_ssl=0 (Postiz connects without TLS; the traffic stays in the network).
  • Bucket: a private S3 bucket, and an IAM role for ServiceAccount ghost in your namespace (IRSA) that may read, write and delete its objects and list it. No key is stored anywhere.
  • Registry, only for images you build yourself: ECR repositories creator-kit/tb-setup, icecast-relay, ghost-bridge.

Then cp k8s/overlays/eks/cloud.env.example <folder>/cloud-eks.env and fill it in.

Google GKE

  • Cluster: PROJECT=<project> REGION=<region> k8s/clusters/gke.sh up (one zone, two nodes, Workload Identity on).
  • Databases: Cloud SQL for MySQL 8 and for Postgres 17, and a Google service account with the Cloud SQL Client role, tied to Kubernetes ServiceAccount cloud-sql in your namespace. Pods reach the databases through the Cloud SQL Auth Proxy beside them.
  • Bucket: a private Cloud Storage bucket, a service account that may use only it, and an HMAC key for it (Ghost uses Cloud Storage's S3-compatible side).
  • Registry, only for images you build yourself: an Artifact Registry Docker repository.

Then cp k8s/overlays/gke/cloud.env.example <folder>/cloud-gke.env and fill it in.

The site's secrets for a cloud

  • secrets/ghost.env (secrets/puppi3.env in a site made before kit 1.2.0): Ghost's login on the cloud's MySQL (its master user and password, and the database's name).
  • secrets/cloud.env: Postgres's master login (POSTGRES_MASTER_USER, POSTGRES_MASTER_PASSWORD); a job makes Postiz's own logins with it.
  • secrets/s3.env (GKE only): the HMAC key.
  • secrets/ghost-mail.env: Ghost's mail.

The examples are in k8s/examples/, and the Settings reference lists every line. Then (the kit's images are the release's: building your own only for a changed kit, the images) k8s/up.sh <folder> eks --render (or gke), and up.

Test before the DNS

Before pointing the domain at the cloud, check it through its own address: put yours in TRUSTED_EXTRA (behind Cloudflare, nothing else gets in), then

curl -k --connect-to example.com:443:<traefik's EXTERNAL-IP>:443 -sI https://example.com/

Upload a picture to a draft in Ghost: if it shows, Ghost can reach the bucket. Take your address out of TRUSTED_EXTRA once the DNS points at the cloud.

Checking that the kit works

For whoever changes the kit (to try it for your own site, use the try-out instead): on your own computer, Linux, a Mac or Windows inside WSL2, the kit can build a throwaway site, check every part end to end, then remove it. It never touches a real site.

kit/test.sh                               # Compose: the site kit.test
k8s/test/test.sh                          # Kubernetes, on a k3d cluster it makes (local overlay)
k8s/test/test.sh --overlay k3d-eks        # the eks overlay, with stand-ins for RDS and S3
k8s/test/test.sh --overlay k3d-gke        # the gke overlay, with stand-ins for Cloud SQL and Cloud Storage
k8s/test/test.sh --render-only            # every overlay rendered and checked, no cluster (a minute)

The Compose test needs ports 80, 443, 8222 free (LIVE_PORT=<another> kit/test.sh for the stream's), ffmpeg, Python 3, Node.js 20 or newer and a browser for it (npm install and npx playwright install --with-deps chromium in kit/theme-test/); it says what's missing; the Kubernetes ones also need k3d, kubeconform and 12 GB of memory for Docker. --keep leaves the site up to look around.

Changing things later

  • A setting: edit site.env or a file in secrets/, then start again (kit/kit.sh <folder> up -d, or k8s/up.sh <folder> <overlay>). Only the parts that use it restart.
  • A module: change MODULES and start again. A module switched off has its alerts taken out of Grafana too. Switching live on later needs only its DNS name and the theme's Live stream URL: its passwords were made at setup.
  • Phone notifications: NTFY_URL in site.env is the one place for both the bridge and Grafana's alerts (empty = none); start again and kit.sh restarts Grafana for it.
  • A network: change NETWORKS (the dashboards' sections and the bridge's collectors) and CHANNELS (where posts go).
